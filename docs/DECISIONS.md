## Additional Phase 1 choices (flagged for review)

- Logo formats are PNG, JPEG, WebP (API.md said PNG/SVG). SVG is refused on purpose: it can carry script. Min 256 px both sides, aspect 0.8 to 1.25, max 2 MB, re-encoded on save (strips metadata and appended bytes).
- Handle rule is 3 to 30 of letters, digits, dot, underscore (stricter than API.md examples): LinkedIn company slugs with hyphens or slashes (`company/acme-bank`) are rejected for now.
- Account `handle` is stored bare and returned in display form (`@` prefix for instagram, x, youtube) as in API.md; `url` has no scheme as in API.md.
- A failed reachability check never blocks adding an account: it is saved with `status: "unreachable"` and a `warning` text.
- Refresh tokens are tracked server-side (table `refresh_tokens`), rotated on use; re-using a rotated token revokes all of that user's refresh tokens.
- Login is rate limited in memory (5 failures per email+IP per 15 minutes -> 429). Single process only until Redis arrives.
- Passwords are hashed with bcrypt (72-byte limit enforced at the schema).

## Phase 2 choices (detection engine, flagged for review)

- Engine lives in `backend/app/core/engine/` with no FastAPI/SQLAlchemy/network imports. It only scores; every detection comes out as `status="pending_review"`.
- Allowlist is exact handle / profile URL / package id / App Store id only, checked before scoring. A mirror-site listing (APKPure etc.) of the official package id is NOT official. The brand's exact name never excludes a candidate.
- Verdicts: `flagged` (impersonation likely), `brand_name` (uses the exact name; may be the brand or an impersonator), `review` (uncertain, human look), `safe`. Only `flagged`/`brand_name` get full name points; `review` gets half.
- Why "Acme Bakery/Hotels/Weather" are not flagged: a hit needs the full brand token (or one edit of it with every leftover piece explained by known words). Partial matches on the first word are `safe`, or `review` if the rest is an impersonation word ("Acme Support"). A word list of benign trailing words exists only as a supplement (`BrandProfileInput.extra_benign_words`).
- Edit tolerance is only applied to brand tokens of 5+ letters (two edits: 8+). Typos of very short brands (e.g. "Zoho") are not detected by design; exact, look-alike and combo forms are.
- A one-letter change that yields an ordinary dictionary word ("Acme Bark") is `review`, not `flagged`.
- A leading `@` is treated as a handle prefix and stripped, so `@cmebank` reads as "missing letter", not "a" via symbol swap.
- Logo thresholds (synthetic shape logos, not real brands): >= 80 likely copy, >= 55 similar, below 55 no points. Colour-inverted logos score ~0. Re-tune on real labelled data.
- Score model: reasons sum to `raw_total`; per-category caps are applied inside the reasons; the 100 cap is applied last (`capped` flag). Publisher-difference counts only with another brand signal; 22 when the publisher name resembles the brand, else 20.
- LLM scam-intent check: setting `scam_llm_enabled` (default false); the Anthropic option was removed in E5. Not wired into any endpoint yet.
- Ruff: `E501` is ignored in `app/core/engine/*` and `scripts/*` (regex and word tables).


## Phase 3 choices (collectors, flagged for review)

- **Collectors are providers; `sources` rows are platforms.** A collector (tavily, searxng, itunes, google_play, sample) declares the platforms it covers. A platform is `online` if any covering collector works, `slow` if only slow/partial ones do, else `unavailable`. Per-collector health, back-off and the last good result live in a new table `collector_state` (migration 0002).
- **Auto mode ignores iTunes.** iTunes needs no key, so on its own it does not turn `auto` into `live`; a fresh install must not query real stores for a demo brand. `auto` = live when a Tavily key, a SearXNG base URL or the google-play package is present. Explicit `live` still runs iTunes.
- **Live mode without a key shows honest gaps.** Tavily stays in the live chain and reports `unavailable (no_key)`; sources are never filled with sample data in live mode.
- **Back-off** 1 m, 5 m, 15 m, 1 h, 6 h (capped), reset on success; a provider `Retry-After` (capped at 24 h) wins. Local-config problems (`no_key`, `not_installed`, `not_configured`, `unsafe_base_url`) are re-checked on every scan, not backed off. `invalid_key` is backed off like other failures; a manual retry (the retry button) ignores back-off.
- **Tavily credits:** budget guard is atomic (`UPDATE ... WHERE credits + cost <= budget`), basic = 1, advanced = 2. 4xx answers (401/429/432/433) are refunded because they are not billed; 5xx and timeouts keep the reservation (they may have been billed). The guard uses the larger of our counter and Tavily's reported `usage.credits`. Default budget 900 of the 1000 free credits. Default per-scan cap 12 queries.
- **Partial results are kept:** if a later query of a scan is rate limited, out of budget or fails, earlier results are returned and the source shows `slow` with a note.
- **Tavily uses `include_domains` for the platforms still monitored**, quoted queries with `exact_match`, brand x (support, official, helpline, rewards), aliases/keywords, then look-alike variants (same techniques as the Phase 2 synthetic generator).
- **SearXNG SSRF:** the operator-set base URL must resolve to public addresses (reusing `url_safety.validate_public_url`) unless `SEARXNG_ALLOW_PRIVATE_HOSTS=true`. No DNS pinning is applied to it (operator configuration, not user input).
- **Result URLs are never fetched by default.** Collectors only read provider responses. Optional reachability checks (`REACHABILITY_CHECKS_PER_SCAN`, default 0) go through the SSRF-safe `UrlChecker`.
- **Google Play** goes through an optional, lazily imported package (`google-play-scraper`), not installed, not in requirements. It scrapes Play pages (unofficial; terms-of-use risk and license are unverified). Without it the source reports `not_installed`.
- **Sample collector** carries `source="sample"` on every candidate and `extras.sample_role` (`official_echo`, `lookalike`, `hard_negative`) so tests and the evaluation can check the engine; the role is ground truth, not a score.
- **Retry endpoint is synchronous** in Phase 3 (returns 202 with the result); Phase 4 makes it a job.
- **Settings:** `env_ignore_empty=True`, so `NAME=` left blank in `.env` (as in `.env.example`) means "not set" instead of a parse error. Tests ignore `backend/.env` and block real network/DNS access.
- Audit actions added: `source.monitor_toggled`, `source.retry`, `settings.data_mode_changed`.

## Phase 4 choices (scan pipeline, jobs, screens API; flagged for review)

**Detection rules**
- **Detection rule:** a candidate becomes a detection when it has evidence tied to THIS brand (name, logo/icon or description overlap scored above 0) AND either its score reaches the threshold or the engine flagged its name outright. Account/store oddities alone (young account, unverified, few posts) never make a detection. Threshold = `100 - sensitivity` (sensitivity 50 to 95, default 75, so threshold 25). A flagged name always goes to review; the slider moves the bar for weaker evidence only. This is my design: please confirm.
- **Cleared (false-positive guard):** below threshold but the name partly resembles the brand (verdict not `safe`, or name match >= 25%, which includes "Acme Bakery") is stored with `status="cleared"`. Cleared rows never appear in detection lists, counts or reports; they feed `/detections/false-positives`.
- **Prefilter** (`SCAN_PREFILTER`, default on): no name signal and no brand keyword/domain hit means the candidate is dropped before the logo download and the optional AI check. Trade-off: a logo copy with a completely unrelated name is not found.
- **Human decisions survive re-scans:** `reviewing`, `confirmed`, `dismissed`, `marked_official` are never changed by a scan. A re-scan only updates `last_seen_at`, the score history, evidence (a new snapshot only when the content changed) and, when the score moved by 10 points or more, adds a system note (no reopening). Untouched `new` / `cleared` rows are re-scored and can move between `new` and `cleared` (history event written).
- **Allowlist wins everywhere:** a scan that meets an exact official handle/URL/package/bundle id records an `official_matches` row (reason, matched rule, times seen) and closes any existing detection for it as `marked_official`. Adding an official account/app (Brand Profile page) does the same immediately.
- **Status vocabulary:** wire values stay `new | reviewing | confirmed | dismissed | marked_official` (plus internal `cleared`). "Keep reviewing" = `reviewing` (`keep_reviewing` is accepted as an alias). `marked_official` is not reversible through the API (remove the asset from the allowlist yourself); a decided detection can be moved between reviewing/confirmed/dismissed.
- **Mark as official limits:** only Google Play / App Store apps (a third-party APK listing is never official) and handles up to 30 characters (allowlist column size). Telegram is accepted for mark-official although the Brand Profile form does not offer it yet.
- **Scan statuses:** `queued | running | completed | partial | failed` (column `scans.state` keeps its name; the API also returns the old job vocabulary `state: queued|running|done|error`). `partial` = at least one source unavailable or returned partial results. `failed` = an internal crash, or EVERY active source unavailable with nothing (not even cached results) to analyse. A queued/running scan older than `SCAN_STALE_MINUTES` (30) is failed automatically so scans can start again.
- **One scan per brand:** the second start returns 409 with the running scan (`job_id`, `scan`). Enforced in the application (check then insert), not by a database constraint: two requests in the same millisecond on different servers could both pass. Acceptable for one brand/one API process; revisit with a partial unique index on Postgres.
- **Evidence:** snapshot = canonical JSON of the candidate (fetch time excluded), stored at `DATA_DIR/evidence/<sha[:2]>/<sha>.json`, so identical content is stored once. The endpoint re-hashes the file and reports `hash_verified`. Screenshots: hook only (`SCREENSHOTS_ENABLED`, Playwright not installed, not tested live).
- **Logo fetch:** result URLs go through the new `core/pipeline/image_fetch.py` (same SSRF rules as `url_safety`, plus size/type/magic checks, 25 downloads per scan). Only for live candidates with an icon URL; sample data never triggers a download. Any failure is recorded as "Logo unavailable: <why>" and the candidate continues. Result pages are NOT fetched (no og:image scraping): only the image URL a source supplies.
- **Optional AI text check** runs only when `SCAM_LLM_ENABLED=true` AND the active provider has a key; never for sample data; failures are skipped silently (counted). When enabled without a key the scan records a note.

**Jobs and scheduler**
- `REDIS_URL` set: RQ queue `scans` (`python -m app.worker`, SimpleWorker on Windows). Unset: in-process thread. If Redis is unreachable when queuing, the scan falls back to a thread (logged). `SCAN_EXECUTOR=inline` runs synchronously (tests).
- Scheduler: in-process loop started by the app lifespan unless `APP_ENV=test` or `SCHEDULER_ENABLED=false`. Interval = `SCAN_INTERVAL_MINUTES` (env wins, `0` = off) else the Settings schedule (`off|5m|15m|1h|1d`, default `1d`; "off" is an addition to API.md). With several API processes each runs a loop; the one-running-scan rule and the "last scan" check keep it to one scan, but run the scheduler in one process only.
- **Credit-aware rule** (pure function `decide_schedule`, only when Tavily is in the live chain): cost per scan = max queries x credits per query (12 x 1). Keep one scan's worth in reserve for manual scans. If less than one scan remains above the reserve, scheduled scans pause until the 1st of next month. Otherwise the interval is stretched to `days_left x 24h / affordable_scans` if that is longer than the configured one (so "hourly" with 900 credits becomes about every 6 hours at mid-month). Manual scans are never blocked by this rule, only by the hard Tavily budget guard.
- Notifications (email, high-risk alert, weekly digest, webhook) are stored preferences only: **nothing is sent**. `GET /settings` says `delivery: "not_implemented"`. Webhook URLs are shown to admins only (they often contain a secret token).

**Screens**
- Lists default to the current effective data mode (`sample` shows only sample rows, `live` only live rows); `source=all` or `source=sample|live` overrides. Every list/aggregate carries `data_mode` and `is_sample`.
- Look-alike lab: `official` = exact allowlisted handle/package, OR the typed text is exactly the brand name/alias (`official_basis: "name"`, with the reminder that real scans never exclude by name). `review` verdicts are shown as `not_flagged` (with `engine_verdict`). Settings rules switch off techniques: a flagged name whose techniques are all off becomes `review` in the lab and in scans. The 12 default cases are written for "Acme Bank" and seeded once (an admin's deletions are respected).
- Reports: created as DRAFT from `detection_ids` or, by default, the confirmed detections; the rows are snapshotted. Formats are `csv` and `html` (printable, browser Print to PDF). **No PDF**: no PDF library is installed and none was added. Approving is a person's action (audited). Nothing is sent anywhere.
- Evaluation: synthetic numbers (5 built-in brands, seed 7) cached in memory per process and labelled optimistic; real precision only from reviewer decisions (confirmed / (confirmed + dismissed)); recall of real detections cannot be measured.
- Audit actions added: `scan.started`, `scan.finished`, `detection.status_changed`, `detection.marked_official`, `report.generated`, `report.approved`, `settings.updated`, `lookalike.case_added`, `lookalike.case_removed`, `lookalike.cases_run`, `evaluation.run` (plus the existing `account.added`, `app.added`, `source.monitor_toggled`, `settings.data_mode_changed`). `scan.started`/`finished` by the scheduler carry actor `scheduler`.
- Migration `0003_scan_pipeline` (SQLite batch mode, also written for PostgreSQL but **not run on Postgres**).

## Phase 6 choices (deployment readiness; flagged for review)

- **Old product removed.** The old product backend and its 9 orphaned frontend pages were deleted; the new stack (api, worker, db, redis, frontend) lives in `backend/` and `frontend/`.
- **Compose layout:** Postgres `17-alpine` (pinned major; migrations were tested on a local PostgreSQL 18.1, not on 17), Redis 7.2 (last BSD-licensed line, see DEPENDENCIES.md) with a password, named volumes `pgdata`, `redisdata`, `scammind-data` (DATA_DIR, shared by api and worker). Secrets are required by `${VAR:?}` (compose refuses to start without POSTGRES_PASSWORD, REDIS_PASSWORD, JWT_SECRET, ADMIN_EMAIL, ADMIN_PASSWORD); no default secrets exist anywhere. Db/redis publish no ports; api and frontend bind to 127.0.0.1 (put a TLS reverse proxy in front for any real use). `docker-compose.dev.yml` (explicit `-f`, not an auto-loaded override, so it cannot slip into production) publishes db/redis on localhost.
- **Migrations in containers:** `docker-entrypoint.sh api` runs `python -m scripts.migrate` first. The script takes a PostgreSQL advisory lock, so replicas starting together are safe (tested with three concurrent runs on PostgreSQL 18.1). With many replicas set `RUN_MIGRATIONS=false` and run one `migrate` job. The worker never migrates; compose starts it only after the api is healthy.
- **One scheduler:** the scheduler loop lives in the API process. In compose the worker has `SCHEDULER_ENABLED=false`; if you scale the api, set it to `false` on all replicas but one. (The one-active-scan index now makes a duplicate scan impossible, but extra loops would waste credits checking.)
- **Image details:** Python 3.12-slim, multi-stage (builder venv only holds runtime requirements: no pytest/ruff), non-root uid 10001, `/data` volume, healthcheck on `/health/live` (liveness, no dependencies). Frontend: Vite build served by `nginxinc/nginx-unprivileged` on port 8080 with SPA fallback and security headers (CSP, nosniff, frame deny, referrer, permissions, HSTS). **The API address is a runtime setting** (`API_URL` -> `/config.js`), so one image works for every environment; `VITE_API_URL` is only the build-time fallback. The CSP allows Google Fonts (index.html still loads Manrope from there: self-host the font if you want a stricter policy). **Neither image was built here (Docker is not installed on the authoring machine); `docker compose config` and hadolint were not run.**
- **Postgres review (models and migrations):** read for JSON, batch ops, defaults, enums and index names. There are no DB enums (string columns), JSON columns carry only Python-side defaults or string `server_default`s that PostgreSQL casts, batch mode is a no-op on PostgreSQL, and all index/constraint names come from the naming convention. The full suite (including migrations 0001-0004 vs the models) was run against a real throwaway PostgreSQL 18.1: see DONE_AUDIT.md for numbers. pgvector is NOT used (documented optional: a future embedding-based logo/text similarity could store vectors with it).
- **Migration 0004** adds two partial unique indexes (SQLite and PostgreSQL syntax): `uq_scans_one_active_per_brand` (one queued/running scan per brand; request_scan turns the IntegrityError into the normal 409) and `uq_lookalike_cases_builtin_name` (the 12 default cases are seeded once even with several API processes). It first cleans existing duplicates (keeps the newest active scan, fails the others; keeps the oldest built-in case per name). Downgrade drops both indexes.
- **/health** is now a readiness check: database, migration revision vs head, Redis, RQ worker registration, data dir (writable, free space), and per-collector configuration/last-known state, with NO live third-party call. Public `/health` (and `/api/health`) returns only the overall status and one word per component; `/api/health/details` (admin) adds reasons, ages, revisions and counts. 503 only when the database is down; everything else degraded is 200. `/health/live` is the liveness probe. A database created without Alembic (tests, e2e) reports migration `unknown`; in `APP_ENV=production` a missing `alembic_version` is `degraded`.
- **Sentry:** optional, env-driven (`SENTRY_DSN`, `SENTRY_ENVIRONMENT`, `SENTRY_TRACES_SAMPLE_RATE`), lazy import, in `requirements-extra.txt` (not core). `before_send` removes request bodies, cookies, query strings, auth headers, user identity, local variables and any configured secret. No frontend Sentry hook (it would need a new npm dependency).
- **Canary:** `app/services/canary.py`, `python -m scripts.canary`, `POST /api/health/canary` (admin; audited). Apps are scored without a logo comparison there, so the canary requires the fake app to be stored for review with name + publisher signals (low band) rather than medium/high. It proves the pipeline logic, not that live sources work.
- **Tests on PostgreSQL:** `TEST_DATABASE_URL` (deliberately not DATABASE_URL, so a real database can never be pointed at by accident) turns every in-memory test engine into its own random schema of that database. File-based SQLite engines (migration tests, race test) stay SQLite.

## Sample logo variants (flagged for review)

- **Why:** sample candidates had no image, so every one reported "logo unavailable", the logo / icon points (up to 28 / 30) were never earned and sample scores topped out near 70.
- **How:** when the brand has an uploaded logo, the sample collector gives each look-alike and hard negative a GENERATED image (`app/core/collectors/sample_images.py`): `near_copy` (full-size near-lossless JPEG re-save), `resized`, `recoloured`, `cropped`, or `unrelated` (seeded abstract image). Bytes live in the in-memory field `Candidate.inline_image`; they are never serialized (cache, evidence snapshots). Without an uploaded logo no images are made and "Logo unavailable" stays the honest answer (scores then stay below High).
- **Safety:** the pipeline reads `inline_image` ONLY when `source == "sample"` (`_logo_step`); for every other source the field is ignored and the normal SSRF-safe fetch path runs unchanged, so a live collector cannot smuggle bytes in (tested). No network is used for sample images.
- **Honesty markers:** `details.logo` carries `origin: "generated_sample"` + `variant` + a note; the evidence snapshot's `extras` has `logo_image: "generated_sample"` and `logo_variant`; the detection source stays `sample`.
- **Tiers:** look-alikes are `strong` (scam-word name, lure bio, 3-12 day old account, copied logo, scam-page follower pattern), `medium` (edited logo, lure bio, 20-55 days) and `weak` (name only, unrelated picture, old account, neutral bio, stays Low). Hard negatives keep an unrelated image. Apps: strong = APK-mirror copy with `near_copy` icon, different publisher, few installs, new listing; medium = edited icon, few installs; weak = unrelated icon. Scorer weights and bands are UNCHANGED; the only engine-adjacent change is that `Candidate.to_engine` passes `extras["installs_count"]` (an int) as `CandidateApp.installs`.
- **Honest ceiling (read this):** an app can reach at most 24 name + 30 icon + 22 publisher + 4 mirror + 3 installs + 2 new listing + 1 ratings = 86, because the brand has no store description to overlap with. Strong sample apps therefore land exactly at 85 only when the icon copy scores >= 90 (not guaranteed for every logo) and the name match is ~96%+. The perceptual hash is also unstable on perfectly symmetric logos (the seed test logo scores ~76-82 after any re-encode except the near-lossless `near_copy`), which is why `near_copy` is full size and q100. Re-tune on real logos.
- **Re-seeding:** sample rows are keyed by (platform, handle), so after the generator changed old rows would stay beside the new ones. Plain `python -m scripts.seed_test_brand` reuses the brand and updates same-key rows (human decisions are kept); `--reset-sample` first deletes ONLY the brand's `source="sample"` detections / cleared rows and their events (`app/services/sample_reset.py`, direct DB call using DATABASE_URL), then rescans. Live rows, brand data, settings and users are never touched. It removes human decisions made on sample rows too; they are sample data.



## Extension E1-E4 decisions (2026-10-14; flagged for review)

Decisions D1 to D13 of `docs/EXTENSION_PLAN.md` as answered by the owner, and what was built.

- **D1 severity beside band.** `severity` LOW / MEDIUM / HIGH / CRITICAL added; `band` and its 85 / 70 cutoffs and every existing score are unchanged (a golden file produced by the code before the change, `tests/fixtures/golden_scores_v1.json`, pins every sample score, band and reason). Severity cutoffs: LOW < 40, MEDIUM 40-69, HIGH 70-84, CRITICAL 85+, configurable by `SEVERITY_MEDIUM_MIN` / `SEVERITY_HIGH_MIN` / `SEVERITY_CRITICAL_MIN` (must satisfy 0 < medium < high < critical <= 100). The 40 cutoff is my proposal: please confirm it.
- **D4 weights.** Original social and app weights are frozen as `WEIGHTS_V1` (algorithm version `1.0`, stamped on social and app detections; the scorer code is called unchanged). New signals use algorithm `2.0` with `WEIGHTS_V2_WEB`: domain_similarity 40, rapidfuzz_similarity 12, deceptive_subdomain 20, idn_homograph 15, added_words 10, url_reputation 45 (total capped at 100). **These new weights need your approval.** A Safe Browsing match is its own signal (45), not folded into name points.
- **Signals.** Each detection stores `signals[]` in `details` (not in `evidence`: that column is the hash-verified snapshot record). `unavailable` (could not check) is never `clean` (checked, nothing found); `value` is null for unavailable. Provenance: `real_api`, `local_algorithm`, `pretrained_model` (reserved), `synthetic` (all sample data).
- **D2 RapidFuzz** only as an additional signal for domains, and only when the home-grown matcher said `safe`, so no existing verdict moves and hard negatives such as "Acme Bakery" stay clean. `name_match.py` is unchanged.
- **D8 web category.** `category=web`, `type=lookalike_domain`, `platform=web`, one detection per normalized host. The candidate gate: the domain resembles the brand (name matcher verdict not safe, deceptive subdomain, IDN homograph or RapidFuzz). Domains are compared by registrable domain (tldextract's bundled Public Suffix List snapshot, `suffix_list_urls=()`, no cache dir, no runtime network). A TLD missing from the snapshot (`.test`, new gTLDs) is treated as a one-label suffix. Raw IP hosts (also decimal, hex and octal forms) are recognised and not compared. The UI has no Web list yet (E9); web rows count in the Dashboard totals and in the API.
- **Sample web candidates** use the reserved `.test` TLD only, so no real website is implied; they are labelled `synthetic` and never sent to Google. The sample scan now has web candidates: tests that counted sample rows were updated (official excluded 3 -> 4, category split).
- **D11 Safe Browsing.** Lookup API **v4** `threatMatches:find` (read on developers.google.com/safe-browsing/v4/lookup-api on 2026-10-14: POST, body `client` + `threatInfo`, max 500 URLs per request, `matches` or `{}`). I could not confirm which version Google recommends for new work, so the adapter is isolated in `app/core/providers/safe_browsing.py` and can be swapped (v5, or Web Risk for a commercial product). Non-commercial use only. The key travels in the `x-goog-api-key` header, never in the URL. Verdicts: match / clean / unknown / failed (table in API.md 20.3); `clean` means "no match in Google's lists, not a safety guarantee". Only candidates that already resemble the brand are sent, in one batch per scan (500 per request), at most 100 per scan. The per-day request budget (default 5000) is OUR limit because the Google pages used here give no quota number. 429 handling: wait for `Retry-After` (default 1 h) and report `unknown`. A scan never fails or turns `partial` because of Safe Browsing; the effect is visible in scan `counts` and in `GET /api/sources` > `reputation`.
- **Candidate URLs are never visited.** Safe Browsing receives the URL; reachability and logo fetch are not run for web candidates; a test makes any other outbound request fail.
- **D3 (defect).** `official_apps.store_id` (optional numeric App Store id, accepted as number, `id123...` or URL; API only, no UI field yet) plus per-scan learning: when the iTunes listing is matched by its official bundle id, its numeric id is used to exclude the copy that arrives with only the numeric id. The registry itself is never changed automatically. Learning runs before de-duplication because the two copies share one URL and merge.
- **D4 (defect, small).** The same package id with a store it does not have yet adds the store (201) instead of answering 409.
- **D5 (defect).** The scheduler waits for the first official account or app; the reason is shown on `GET /api/scan/status`. `SCHEDULER_ENABLED` still defaults to true and `auto` still means live when a key exists (explained by the reason text, documented in API.md 20.5). Unchanged on purpose: the Setup wizard "Launch" button still scans immediately (it is a manual action).
- **D6 (defect).** Retrying a Tavily-backed source needs `?confirm=true`; the UI shows a dialog with the credit estimate first (Source Health and the App Store sources bar). Otherwise 409 `confirmation_required`; nothing is spent.
- **Not built in E1-E4 (later packages):** `resolution` field, Investigations page, sidebar relabel, Web list in the UI, manual and CSV candidate entry, Gemini / Hugging Face text providers, ImageHash similarity (the package is only listed as optional), brand registry v2, evaluation extensions.

## Extension E5-E7 decisions (2026-10-14; flagged for review)

- **Anthropic removed** (the owner does not use it). Providers: local baseline (always on), Gemini (default AI provider, `GEMINI_API_KEY`, `GEMINI_MODEL` default `gemini-3.5-flash-lite` from the plan: please verify the id with your key), Hugging Face (optional, no default model).
- **Hosted text analysis stays opt-in:** `SCAM_LLM_ENABLED` (default false) is the master switch, so no text leaves the server until you turn it on AND a key exists. `SCAM_LLM_PROVIDER` / the admin setting picks the provider. Only the candidate text (emails, phone numbers and UPI ids replaced by placeholders) and the brand description are sent; never the brand name, handles or URLs. The free Gemini tier may train on inputs (plan section 3).
- **Answers cannot lower scores:** an API likelihood >= 0.6 reuses the existing capped bio input (bio max 28); for app descriptions it is informational. The cache key adds the brand-context hash and kind to model + prompt version + text.
- **Image backend:** default stays `hash` (image-1) so no score moves; `multihash` (image-2) and `imagehash` are opt-in via `IMAGE_SIMILARITY_BACKEND`. ImageHash pulls ~200 MB (numpy, scipy, PyWavelets), so the hashes are also implemented locally; the local wHash is a simplified Haar low-pass hash, not bit-identical to ImageHash.
- **Registry:** still ONE active brand (D10 not lifted); DELETE is a soft archive needing the exact name; verification is a human attestation (method, when, by whom). Domains, accounts and apps stay allowlisted as before; a publisher id is allowlisted only when verified.
- **Provenance:** new `detections.origin` (`scan|manual|import|synthetic`) beside `source` (`live|sample`), so manual rows still show in the live data mode.
- **Intake:** rows that resemble nothing (verdict ignored) are reported `not_flagged` and not saved; the prefilter is off for manual/import rows; their URLs are never fetched, and Safe Browsing is still asked about web rows (looked up, not opened).
- **Not built:** frontend for E7 (Brand Profile fields, Import dialog), embeddings in scans, any live provider call.
